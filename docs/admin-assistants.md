# Владелец и помощники администратора

Подтверждённый владельцем UUID: `3f5f63b8-04b2-4e17-9aa1-16da562c5f72`.
Ник и email не участвуют в определении владельца. Миграция завершится ошибкой,
если этот UUID сейчас не принадлежит активному `profiles.role = 'admin'`.
Она не создаёт нового владельца и не разблокирует существующего автоматически.

## Порядок установки в production

Изменения в GitHub сами по себе **не меняют Supabase**.

1. Развернуть `supabase/functions/admin-reset-password/index.ts` под существующим
   именем **admin-reset-password**. Проверку JWT в настройках не отключать.
   Используются штатные серверные `SUPABASE_URL`, `SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY`; секретный ключ никогда не передаётся браузеру.
   До следующего шага сброс пароля будет отклоняться из-за отсутствующего RPC.
2. В Supabase SQL Editor выполнить целиком
   `supabase/migrations/20261015_owner_and_assistant_admins.sql`.
   Всё выполняется одной транзакцией. При неизвестном формате административной
   функции изменения откатываются целиком: не пропускайте ошибку и отдельные
   проверки ради завершения миграции.
3. Опубликовать обновлённые HTML/CSS/JS. Обновить страницу игры.
4. Проверить три отдельных аккаунта по сценарию ниже. Только затем назначать
   реальных помощников. **Старая production-версия Edge Function сброса пароля
   не считается защищённой этой SQL-миграцией.** Её исходника раньше не было
   в репозитории; развёртывание нового файла обязательно.

## Как назначать

Админ-панель → **Владелец → Администраторы** → поиск по нику → подтверждение
«Назначить помощником администратора». Список показывает класс, дату, назначившего,
состояние и кнопку отзыва. Аватар берётся из существующего bucket `profile-photos`
с действующими правами; при отсутствии фотографии показывается значок.

Помощник открывает ту же админ-панель после обновления игры или повторного входа.
Отзыв сразу прекращает доступ новых RPC-запросов даже со старым JWT.
Уже открытый интерфейс не является источником полномочий.

Точные разрешённые сигнатуры перечислены в `public.assert_admin_operation(text)`.
В видимых модулях нет отдельной формы административной выдачи piCoin и нет
инструмента удаления чужих сообщений/рисунков: новые инструменты здесь не созданы.
Непроверенные production RPC выдачи валюты остаются owner-only до проверки их
определений. Существующие награды промокодов работают через прежние функции.

## Совместимость и защита

`profiles.role = 'admin'` сохранён для совместимости с прямыми проверками роли в
старых RPC и Edge Functions. Различие owner/assistant не хранится в изменяемом
клиентом поле. `admin_staff` хранит назначения и отзыв; клиент не имеет прямого
SELECT/INSERT/UPDATE/DELETE. Существующие администраторы, кроме подтверждённого
владельца, записываются как помощники, а не дополнительные владельцы.

Миграция добавляет внешнюю проверку в существующие PL/pgSQL административные
функции через `CREATE OR REPLACE`, сохраняя OID, параметры, defaults, тела и
имеющиеся authenticated-grants. Неизвестные функции с префиксом `admin_` доступны
только владельцу. Клиентские PUBLIC/anon EXECUTE отзываются. Внутренний quarter
helper не получает authenticated EXECUTE. Неподдерживаемый язык функции вызывает
откат; произвольные SQL-тела автоматически не переписываются.

Дополнительные триггеры защищают профиль владельца, смену ролей, административные
аккаунты и записи назначений. Запись в сезоны/результаты/quarter-таблицы,
DELETE/TRUNCATE карты и истории из пользовательского контекста требуют владельца.
Игровые INSERT/UPDATE пикселей не меняются. Штатные server/cron-вызовы сохраняются.

Это не заменяет production-проверку старых RPC, RLS и отсутствующих в репозитории
Edge Functions. Нельзя проверить из репозитория изменения, сделанные только через
Dashboard. Последующие миграции, переопределяющие admin RPC, должны сохранять
`assert_admin_operation` и запускать тесты доступа.

## Журнал

Триггеры пишут подтверждённые изменения профилей/блокировок, назначений,
промокодов, валютных таблиц, инвентаря, сезонов/четвертей, классов, приглашений,
жалоб, музыки и административных сообщений. В лог не попадают пароли,
IP-адреса, тексты сообщений и рабочие коды промокодов. Запись откатывается вместе
с неуспешной SQL-транзакцией. Отклонённые SQL-вызовы проверяются через серверные
логи Supabase, а не выдаются за сохранённые audit-записи.

Сброс пароля отдельно записывает `authorized`, затем `committed` или `failed`.
Если внешний Auth Admin API отработал, а запись результата в БД не удалась,
Edge Function пишет `PASSWORD_RESET_AUDIT_FAILED` в серверный лог.

Помощник не может читать/изменять/удалять журнал. Хранение — не менее 365 дней;
если pg_cron уже установлен, создаётся ежедневная ограниченная очистка старых
записей (до 10 000 за вызов). Иначе владелец периодически запускает
`select public.prune_admin_audit_log();`. Недавние записи не удаляются.

## Проверки

`tests/admin-access-fixture.sql` — **только для пустой тестовой БД**, не production.
Workflow `Administrative access regression` запускает PostgreSQL 16 в отдельном
контейнере, применяет миграцию дважды и выполняет `tests/admin-access.sql`.
Тесты проверяют ученика, помощника, владельца, заблокированного владельца,
прямые вызовы старых RPC, defaults/SETOF, журнал, отзыв прав с прежним JWT и
внутренний вызов `finish_season → add_season_to_active_quarter`.

Production вручную: отдельными аккаунтами проверить назначение/отзыв, обычную
блокировку, промокод, музыку и просмотр/экспорт сезона. Помощником напрямую
вызвать owner RPC, finish_season, смену роли и Edge Function сброса пароля:
везде должен быть отказ. Проверить журнал владельцем. Проверить поиск и
кнопки на 360/390/430 px. Тестовая схема не содержит всех production-функций.

### Read-only диагностика перед установкой

```sql
select id, role, banned from public.profiles
where id = '3f5f63b8-04b2-4e17-9aa1-16da562c5f72'::uuid;

select p.oid::regprocedure as signature, l.lanname, p.prosecdef,
       p.proconfig, has_function_privilege('authenticated', p.oid, 'EXECUTE') as client_execute
from pg_catalog.pg_proc p
join pg_catalog.pg_namespace n on n.oid=p.pronamespace
join pg_catalog.pg_language l on l.oid=p.prolang
where n.nspname='public'
  and (p.proname like 'admin\_%' escape '\' or p.proname in
       ('get_admin_overview','start_season','finish_season','rotate_season',
        'start_quarter_competition','finish_quarter_competition',
        'add_season_to_active_quarter','clear_map','reset_map','delete_season'))
order by p.proname;
```
