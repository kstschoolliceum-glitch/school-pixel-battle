# Постоянная карта Pixel Battle

Изменения подготовлены для существующей базы. GitHub Pages и Supabase остаются на месте.

## Что изменено

- `js/game-config.js`, `app.js`, `js/loader.js`, `index.html`: централизованные флаги и обновление версий скриптов.
- `js/seasons.js`: загрузка закреплённой карты через `get_permanent_canvas`; сезонные проверки и таймеры остановлены.
- `js/pixel-placement.js`: 1 секунда, защита от повторного запроса, локальный монотонный таймер; награды не сбрасывают ожидание.
- `js/rankings.js`: по умолчанию только ученики за всё время; обновление не чаще раза в 30 секунд.
- `html/*.html`, `style.css`, `js/admin-overview.js`, `js/admin-season-management.js`: скрыты сезонные элементы, временные рейтинги, недельные счётчики и покупка ускорения. DOM-идентификаторы сохранены.
- `js/daily-tasks.js`, `js/pi-coin.js`, `js/unblock-me.js`, `js/sokoban.js`, `js/fifteen.js`: ускорения не предлагаются и не сбрасывают ожидание. Остальные задания, монеты и мини-игры сохранены.
- `supabase/functions/send-scheduled-push/index.ts`: сезонные push пропускаются по серверной конфигурации.
- `supabase/migrations/20261111_permanent_canvas.sql`: серверные правила и защищённые счётчики.
- `tests/permanent*`, `.github/workflows/permanent-canvas.yml`: проверки клиента, SQL, параллельных запросов, повторного применения и браузера.

## Перед применением

Базовая схема, функции ротации и часть триггеров отсутствуют в репозитории. Доступа к рабочему Supabase из этой задачи нет. Поэтому миграция проверяет ожидаемую структуру `place_pixel` и прекращает транзакцию при несовпадении. Не обходите эту проверку удалением условий.

1. Сделайте полную резервную копию базы, включая схему, данные, функции и cron. Проверьте её восстановление на отдельном экземпляре. Сохраните снимок числа строк и контрольную сумму карты.
2. В SQL Editor изучите рабочую схему:

```sql
select id,number,status,is_active,starts_at,ends_at,map_width,map_height
from public.seasons order by starts_at desc;
select pg_get_functiondef('public.place_pixel(integer,integer,text)'::regprocedure);
select n.nspname,p.proname,pg_get_functiondef(p.oid)
from pg_proc p join pg_namespace n on n.oid=p.pronamespace
where n.nspname='public' and p.prokind='f'
  and (p.proname ~* 'season|quarter|reset|rollover|rotate'
    or p.prosrc ~* '(delete from|truncate|update)[[:space:]]+(public[.])?(pixels|pixel_history|seasons|profiles)');
select tgrelid::regclass,tgname,pg_get_triggerdef(oid)
from pg_trigger where not tgisinternal;
-- Если pg_cron установлен:
select jobid,jobname,active,command from cron.job;
```

3. Убедитесь, что ровно одна запись `seasons` имеет `is_active=true, status='active'`. Она может иметь истёкшую дату окончания; миграция сохранит именно эту карту. При неоднозначности сначала выберите карту по её существующим пикселям. Новую пустую карту не создавайте.
4. Изучите вызовы фоновых обёрток: миграция отключает cron с явными упоминаниями `season`, `quarter` и сброса карты в SQL-команде. Непрозрачные функции-обёртки, внешние cron, Edge schedules и сторонние автоматизации нужно отключить отдельно. Не отключайте задачи разблокировки пользователей, чата и прочие независимые задачи.
5. Примените миграцию на копии рабочей схемы, затем выполните сценарии ниже. SQL-fixture в CI проверяет известный контракт; он не заменяет проверку полной рабочей схемы.

## Порядок запуска

1. Применить `20261111_permanent_canvas.sql` в Supabase SQL Editor либо штатным процессом миграций. Повторное применение допустимо до отката.
2. Обновить Edge Function `send-scheduled-push` штатным способом. Остальные Edge Functions не менялись.
3. После успешной проверки базы слить PR и дождаться публикации GitHub Pages. Обновить открытые страницы учеников.

Миграция оставляет старый `season_id`, размеры, все пиксели и историю. `ends_at='infinity'` обеспечивает совместимость старых RPC с проверкой срока; триггер запрещает создание, переключение, удаление и очистку сезонов. DELETE/TRUNCATE карты и истории блокируются, обычные upsert и игровые предметы сохраняются. Код, таблицы и прежние определения функций сохранены; определения изменяемых RPC хранятся в закрытой `pixel_game_private.function_backup`.

Серверное ожидание всегда 1000 мс, включая владельца. Существующий `FOR UPDATE` профиля сериализует запросы одного пользователя. Время обновляется после получения блокировок. Прямые клиентские записи в карту/историю запрещены; бонус не может сдвинуть `last_pixel_at` назад. Покупка/активация ускорения отклоняется, новые таймеры наград не применяются. Прежние таймеры сохраняются, но не влияют на установку. Старые SQL-клиенты могут видеть исторические значения таймеров; новый интерфейс их игнорирует.

## Общий ТОП

Начальный результат — максимум из `profiles.total_pixels` и числа записей истории каждого ученика. Эти значения не складываются, поскольку отражают пересекающиеся данные. Таким образом, прежний результат не уменьшается, а доступная история установок учитывается полностью. При ранее повреждённых завышенных счётчиках автоматическое исправление не выполняется: сначала нужна отдельная сверка.

После запуска каждая новая запись установки добавляет 1 к защищённому счётчику. Повторное применение миграции не пересчитывает исходный результат и не добавляет историю второй раз. Запрос ТОПа использует готовые счётчики, без полного пересчёта истории при каждом обновлении. Исторические недельные/четвертные таблицы и RPC сохранены для архива.

## Проверки

Локально: `node --check` для всех JavaScript и `node tests/permanent-cooldown.cjs`. Браузер и PostgreSQL проверяются workflow `Permanent canvas regression`. Браузер использует mock Supabase: это проверка загрузки, скрытых элементов на 1440 и 390 px, клиентского таймера и защиты от повторного клика, а не полноценная проверка авторизации/Reаltime.

На копии рабочей базы и после выпуска проверить:

- Старые пиксели/контрольная сумма не изменились; перезагрузка и рестарт сохраняют карту.
- Первый пиксель проходит, немедленный второй отклоняется, через секунду проходит. Параллельные API-запросы одного пользователя дают только один успех.
- Прежнее активное ускорение, промокод, награда мини-игры и права владельца не обходят секунду.
- Два реальных ученика видят изменения друг друга; вход и профиль работают.
- ТОП увеличивается на 1 за успешную установку; одинаковый цвет в той же клетке не считается.
- При смене календарной даты карта, общий ТОП и `canvas_id` сохраняются. Сезонные cron отключены, сезонные push не отправляются.
- Предметы, задания, чат и мобильная навигация работают; нет ошибок консоли.

Нагрузочный тест на реальном числе учеников здесь не проводился. При одной установке в секунду сохраняются существующие ежедневные вычисления/история/Reаltime. Оцените задержку RPC, блокировки и сообщения Reаltime на staging перед массовым запуском; при необходимости оптимизируйте после измерения, не меняя хостинг.

## Откат

Откат приложения выполняется вместе с сервером, в окно обслуживания. Новые пиксели и история должны остаться.

1. Остановить запись на время отката, сделать свежий backup.
2. Вернуть предыдущую версию клиентского кода.
3. В транзакции включить `seasons_enabled=true, boosts_enabled=true, permanent_canvas=false` в `pixel_game_private.config`. Восстановить определения из `pixel_game_private.function_backup` через `EXECUTE definition`.
4. Удалить только добавленные этой миграцией триггеры: `permanent_canvas_seasons`, `permanent_canvas_seasons_truncate`, `permanent_canvas_reset`, `permanent_canvas_client_write`, `permanent_canvas_boost`, `permanent_pixel_clock`, `permanent_count_placement`. Не удалять таблицы, историю и приватные счётчики.
5. Проверить `original_season` в конфигурации. Дату окончания назначить осознанно в будущем. Автоматически возвращать истёкшую дату опасно: это может немедленно запустить прежний rollover. Восстановить active-статусы cron из `cron_backup` только после согласования графика.
6. Вернуть прежнюю Edge Function и проверить игру. Для повторного перехода после отката требуется отдельная проверка исходных счётчиков и конфигурации; простое повторное применение рассчитано на работающий постоянный режим.
